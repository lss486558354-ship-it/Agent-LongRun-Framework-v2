# 02 · 铁律二：先写记忆，再输出断点

> **在完成一个执行阶段或触发中断（如 token 预警）时，必须先调用 `save_memory` 存入当前进度和关键决策，然后再输出断点信息。**
> 顺序不能反。断点文本是「已经存好了」的回执，不是「准备去存」的草稿。

断点必须写进**当前项目**的记忆库（`<项目根>/memory.db`），
热状态写到 `<项目根>/.longrun/state.json`。两者共用同一个 `root`。

## 触发时机

- token / 上下文即将耗尽
- 一个阶段完成，准备进入下一阶段
- 等待用户确认、等待外部账号/权限
- 会话即将切换、换机器
- 任务正式完成
- 遇到无法自行解除的阻塞

## 固定顺序

```
1. 生成结构化断点内容（含机器可读标记）
2. 调用 save_memory ──失败──▶ 写 .longrun/pending_checkpoint.json
   │                          └─▶ 抛 CheckpointWriteError，不输出断点
   └─成功─▶ 拿到 memory_id
3. 更新本地状态机并落盘
4. 才允许把断点文本输出给用户
```

## 断点必须包含

| 字段 | 说明 |
|------|------|
| 任务 | 一句话描述 + task_id |
| 类型 | `interrupt` / `phase_complete` / `blocked` / `complete` |
| 状态 | 状态机当前状态、读写门禁 |
| 阶段 | 当前阶段名 |
| 已完成 | 本阶段做完了什么（可验证的结果，不是「在做了」） |
| 关键决策 | 为什么这么选，排除了什么 |
| 下一步 | 恢复后第一件事，必须具体到可执行 |
| 机器标记 | 单行 `<!-- longrun-state: {...} -->` |

## 机器可读标记

断点原文最后一行必须是：

```html
<!-- longrun-state: {"task_id":"T_...","status":"paused","access_mode":"writable",...} -->
```

它是「换机器后只靠记忆重建状态」的唯一依据。
禁止省略，禁止拆成多行，禁止在标记里塞正文。

## 写入失败怎么办

- **不输出断点文本**，明确告诉用户「记忆写入失败，断点未输出」
- 保留 `.longrun/pending_checkpoint.json`，等记忆服务恢复后重试
- 不允许「先口头告诉你断点，回头再补写」——回头往往就没有回头

## 反模式

- ❌ 先打印断点，再调用 `save_memory`
- ❌ 只写「继续做」三个字，没有下一步
- ❌ 断点只存在聊天记录里，没有 memory_id
- ❌ 写入失败仍然输出断点，让用户误以为已保存
